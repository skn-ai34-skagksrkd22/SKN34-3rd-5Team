# 루트 고유 번호 인계

루트는 게시판 글의 `postNumber`와 별개인 `routeNumber`를 갖는다. 표시 형식은 `000001`~`999999`의 숫자 6자리 문자열이다. 게시글 000001과 루트 000001은 서로 다른 대상이므로 관리자는 종류와 번호로 검색한다. 기존 `TripRoute.id`와 URL은 변경하지 않는다.

## 현재 프론트

- 루트 카드와 상세에 루트 번호를 표시한다.
- 샘플 6개는 000001~000006의 고정 번호다.
- 기존·신규 로컬 루트는 처음 목록 또는 상세에 표시할 때 별도 localStorage 등록부에 번호를 할당한다. 현재 글 생성 서버 API가 없으므로 서버 발급을 대신한 로컬 미리보기다.
- 등록부는 루트 ID에 번호를 연결하며 삭제 시에도 항목을 보존한다. 수정·정렬·재접속에 번호를 유지하고 삭제 번호를 재사용하지 않는다.
- Web Locks로 같은 출처의 여러 탭 발급을 직렬화한다. 저장 실패·등록부 손상·번호 소진 시 번호를 임의로 재발급하지 않고 ‘번호 확인 필요’를 표시한다.
- 브라우저 데이터 삭제 또는 다른 브라우저에서는 동일 번호를 보장하지 않는다. 여러 사용자의 공용 번호나 관리자 검색에 이 로컬 번호를 사용하면 안 된다.
- API에서 `routeNumber`를 받으면 그 번호를 우선 표시한다. 로컬 예시 번호를 서버 번호로 확정하거나 업로드하지 않는다.

## 백엔드 구현 요청

1. Django 모델·마이그레이션으로 루트 전용 공통 sequence/identity와 고유 번호를 관리한다. 게시판 일련번호와 독립적으로 발급한다.
2. 코스 저장 트랜잭션 성공 시 읽기 전용 `routeNumber`를 반환한다. 생성·목록·상세 응답에 동일한 값을 포함한다. 예: `{ "id": "server-id", "routeNumber": "000007" }`.
3. 수정·구장 변경·소유자 변경에도 번호를 유지한다. 삭제 번호를 재사용하지 않으며 롤백에 따른 공백은 허용한다.
4. 여러 사용자 동시 저장에도 중복되지 않도록 DB unique 제약을 적용한다. 클라이언트의 번호 지정·변경을 허용하지 않는다.
5. 999999 도달 시 재사용·뒷자리 절삭 대신 신규 발급을 제한하고 운영자에게 알린다. 소진 전 번호 확장 정책을 별도로 합의한다.
6. 관리자에서 종류=루트 + 번호로 검색하도록 한다. 글 게시와 루트 저장의 관계를 분리해, 루트를 소개하는 게시글이 있다면 각자의 번호를 유지한다.

실제 서버 API, 테이블, 관리자 검색은 아직 구현하지 않았다. DB 변경 없이 프론트와 계약만 준비했다.
