# 먹거리 플레이스 추천 — 반경·분리·자동화 정책 (2026-09-08, 최종 확정)

9/7~9/8 이틀에 걸쳐 논의한 걸 최종 결정으로 정리합니다. 대상 파일: `crawling/collect_kakao_places.py`, `crawling/README.md`, `data/raw/구장먹거리,컨텐츠.xlsx`(Food Stores 시트).

## 1. 반경 기준: "성인 남성 도보 30분" → 2.5km(2500m)로 확정

- 계산 근거: 도보 평속 80m/분(4.8km/h, 국내 상권분석·부동산에서 흔히 쓰는 "도보 10분=800m" 표준) × 30분 = 2400m
- 팀 논의에서 계산값 2400m를 쓰기 편한 숫자로 반올림해서 **2500m(2.5km)로 최종 확정**
- 음식점(FD6)·카페(CE7)·관광명소(AT4) 세 카테고리 반경을 전부 2500m로 통일 (기존 1000m/1000m/1500m)
- `collect_kakao_places.py`에 `WALK_30MIN_RADIUS_M = 2500` 상수로 반영 완료, device에 커밋 완료

참고: 도심 구장(잠실 등)은 원래도 1km 안에서 카테고리당 45건(API 페이지 한도)이 다 찼던 경우가 많아 반경을 늘려도 결과가 거의 안 바뀝니다. 대전·창원처럼 상권이 덜 밀집된 구장에서 이번 확장 효과가 두드러질 걸로 예상합니다.

## 2. 내부 vs 주변 — "분리하기"로 최종 확정 (합치지도, 폴백하지도 않음)

**카카오 API로 완전 대체(내부 매점까지 전부 카카오로)** 안과 **분리하기(두 데이터 유지, 답변만 분리)** 안을 놓고 논의한 결과, **분리하기**로 정했습니다.

- **왜 완전 대체를 안 하는지**: 카카오 API가 구장 내부 매점을 촘촘히 커버하지 못합니다. 실제로 카카오 867건 중 "구장 내부"로 잡힌 건 27건뿐이었고, 그중 진짜 기존 매장과 같은 게 4건, 신규 후보 18건, 오분류 5건이었습니다. 임시 매대·구단 직영 매점처럼 카카오맵에 별도 장소로 등록 안 된 곳은 카카오로 아예 못 찾습니다. 게다가 카카오 응답엔 영업시간·상세 메뉴가 없어서, 이미 확보한 Food Stores 284건(공식자료, 출처·상태값 다 추적됨)의 정보량을 잃는 손해가 큽니다.
- **분리하기가 왜 되는지**: "합칠 때 생기는 중복 판정 문제"(대전 오분류 5건, 대구 중복 4건 등)는 두 데이터를 같은 답변에 같이 보여주려고 할 때만 생깁니다. 아예 답변 단계에서부터 질문 종류를 나누면, 애초에 두 데이터가 섞일 일이 없어서 중복 문제 자체가 발생하지 않습니다.

**최종 규칙**:

| 질문 유형 | 사용 데이터 | 비고 |
| --- | --- | --- |
| "구장 안에 뭐 있어?" (내부 매점/시설) | Food Stores 284건 (공식자료) 만 | 카카오 데이터 관여 안 함 |
| "구장 주변에 뭐 먹을 데 있어?" (코스 추천) | external_places.csv (카카오) 만 | Food Stores 관여 안 함 |

두 데이터를 합치는 작업(`food_stores_dedup.py`)과, 한쪽에 없을 때 다른 쪽으로 보충하는 폴백 로직 둘 다 채택하지 않습니다. 대구 신규후보 18건 같은 항목은 "구장 주변 추천" 쪽 답변에서는 이미 나오고 있고, "공식 매점 목록" 쪽에는 당장은 안 들어갑니다 — 데이터가 사라진 게 아니라 두 기능이 서로 다른 소스를 쓰는 것뿐입니다.

## 3. 신선도(자동 갱신) 관리 — 소스별로 다르게

두 데이터는 성격이 달라서 갱신 방법도 다르게 갑니다.

**카카오 쪽 (external_places.csv)**: API 호출이라 자동화가 쉽습니다. 주 1회~월 1회 저빈도 재실행을 권장합니다. 단, 카카오 로컬 DB 자체도 폐업·이전 반영이 늦을 수 있어서 "자동 갱신 = 항상 100% 최신"은 아니라는 점은 감안해야 합니다. 현재 Windows 작업 스케줄러에는 `kbo_standing.py`·`kbo_schedule.py`만 등록돼 있고, `collect_kakao_places.py`는 아직 미등록(수동 실행)입니다.

**Food Stores 쪽 (284건, 수동 조사)**: API가 아니라 사람이 구단 공식 자료를 보고 정리한 거라 자동 재수집이 불가능합니다. 대신:

1. **이미 "Verified At"(확인일) 컬럼이 존재함을 확인했습니다** — `구장먹거리,컨텐츠.xlsx`의 `Food Stores` 시트를 열어 직접 확인한 결과, `Evidence Type` / `Source ID` / `Source URL` / `Verified At` / `Status` / `Notes` 컬럼이 이미 4행(헤더)부터 갖춰져 있고, 현재 전 항목이 `확인일 2026-09-04`로 기록돼 있습니다. 즉 새로 만들 필요 없이 챗봇이 이 `Verified At`/`Status` 값을 그대로 읽어서 "이 정보는 2026-09-04 기준입니다" 같은 안내 문구를 자동으로 붙일 수 있는 구조가 이미 마련돼 있습니다. (이건 RAG 프롬프트/체인 쪽에서 이 필드를 실제로 활용하도록 구현해야 효과가 있습니다 — 데이터에 필드가 있는 것과 챗봇이 그걸 답변에 반영하는 건 별개 작업입니다.)
2. **주기적 수동 재검토는 별도 일정으로 관리**: 완전 자동화는 안 되니, 학기/시즌 단위(예: 다음 시즌 개막 전 1회)로 팀이 재검토하는 걸 일정에 넣어두는 걸 권장합니다. 이번 학기 프로젝트 범위에서는 지금 확보한 2026-09-04 기준 데이터를 그대로 쓰고, 재검토는 "다음에 할 일" 목록에 남겨둡니다.

## 4. RAG(챗봇 학습)에 이 구조가 맞는지

이 프로젝트는 LLM을 직접 파인튜닝하는 게 아니라 RAG(검색 증강 생성) 구조입니다 — Chroma 벡터DB에 데이터를 임베딩해두고, 질문이 오면 관련 내용을 검색해서 LLM 프롬프트에 넣어주는 방식입니다. 그래서 "학습이 잘 될까"는 정확히는 "이 데이터 구조가 RAG 검색·답변에 잘 맞을까"의 문제입니다.

- **메타데이터 태깅(Stadium Code, Category, Evidence Type, Status, Verified At)이 이미 돼 있는 건 RAG에 유리한 조건**입니다. 검색할 때 이 값들로 필터링(예: 특정 구장 + 카테고리만 검색)할 수 있고, 프롬프트에서 "Evidence Type이 THIRD_PARTY_API면 정보 출처를 명시하라", "Status가 OPEN이면 안내 문구를 붙여라" 같은 규칙을 지시할 수 있습니다.
- **"내부 vs 주변" 분리는 RAG의 검색 라우팅 단계에서 구현해야 하는 부분**입니다. 두 가지 방식이 있습니다: (a) Chroma에서 두 데이터를 별도 컬렉션으로 나누고 질문 의도에 따라 다른 컬렉션을 검색, 또는 (b) 하나의 컬렉션에 `place_scope: INTERNAL/EXTERNAL` 같은 메타데이터를 붙이고 검색 시 필터로 거르는 방식. 질문이 "내부"인지 "주변"인지 판단하는 건 간단한 키워드 규칙이나 짧은 분류 프롬프트로 충분할 걸로 보입니다.
- 이 라우팅·프롬프트 설계는 아직 이 세션에서 다룬 적이 없는, LLM/백엔드 담당(이현준/임형준/최인영)이 실제로 구현해야 하는 부분입니다. 필요하면 이 정책을 바탕으로 한 구체적인 청킹/메타데이터 스키마·프롬프트 설계 가이드를 별도로 만들어드릴 수 있습니다.
