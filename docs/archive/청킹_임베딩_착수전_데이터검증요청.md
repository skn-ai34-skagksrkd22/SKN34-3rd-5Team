# 청킹·임베딩·벡터DB 작업 착수 전 — 데이터 검증 요청

작성: 2026-09-08 밤. 데이터 전처리 담당(형준님 쪽)이 오늘로 전처리 단계를 마감하면서, 내일(9/9)부터 청킹·임베딩·벡터DB 저장을 맡을 팀원들께 드리는 문서입니다.

**이 문서의 목적은 "다 끝났다"고 선언하는 게 아니라, 여태 수집·전처리한 데이터에 남아있는 문제가 없는지 청킹 작업을 시작하기 전에 한 번 더 직접 확인해달라는 요청입니다.** 아래에 저희 쪽에서 파악한 파일 목록·스키마·이미 알고 있는 이슈를 정리했지만, 저희가 놓쳤을 수 있는 부분(청킹 관점에서만 보이는 문제, 실제 임베딩해보면 드러나는 이상치 등)은 저희가 확인할 방법이 없으니 이 관점에서 다시 봐주시면 좋겠습니다.

## 3. 공통 관례 (대부분의 파일이 따르는 규칙)

- `status` 값: `CONFIRMED`(공식 확인 완료) / `PARTIAL`(불확실성 있음, 답변 시 문구 필요) / `RECHECK`(재확인 필요, 확정 수치처럼 안내 금지) / `OPEN`(예외 미확인, 공통기준 적용 중) / `CONFIRMED_BASELINE`(예외 없음이 확인됨) / `HISTORICAL_ONLY`(과거 정보, 현재 유효성 불명)
- `evidence_type` 값: `OFFICIAL` / `DERIVED` / `THIRD_PARTY_API` / `UNOFFICIAL` — 이 4개로 통일하는 게 원칙
- `evidence_subtype`: 위 4개보다 세분화된 원본 출처 표시(예: `OFFICIAL_TEAM_SITE`, `COMMUNITY_WIKI`, `NEWS_MEDIA`)를 보존하는 보조 컬럼 — 있는 파일도 있고 없는 파일도 있음
- **PARTIAL/RECHECK/UNOFFICIAL이 붙은 행은 챗봇이 확정된 사실처럼 답하면 안 되고, 원본의 불확실성 문구를 그대로 살려야 합니다.** 이건 각 파일 개별 README에 더 자세히 있습니다.

## 4. 파일 간 겹침·조합이 필요한 부분 (청킹/검색 설계에서 신경 써야 함)

- **대전·광주·대구 주차**: `구장교통정보.csv`와 `구장잔여정보_좌석주차버스.csv` 두 파일에 겹치는 정보가 있습니다. 광주·대구는 `구장교통정보.csv`(더 최근 조사)를 우선 사용하면 됩니다. 대전은 원래 두 파일에 정보가 나뉘어 있었는데(본구장 지하주차장 총 수용면 1,220면은 `구장잔여정보_좌석주차버스.csv`에만, 게임데이 운영조건은 `구장교통정보.csv`에만) — **이건 청킹 전에 데이터 쪽에서 고칠 수 있는 문제라 2026-09-08 밤에 바로 수정했습니다.** `구장교통정보.csv`의 대전 지하주차장 행(`PARKING_MAIN_UNDERGROUND`) 하나만 검색돼도 "총 1,679면(지하 1,220면+지상 459면) 중 게임데이엔 지하 1층만 개방"이라는 완결된 답이 나오도록 `details` 텍스트와 `parking_spaces` 컬럼을 자기완결적으로 채웠습니다. 두 파일 자체는 여전히 별도로 남아있고 `overlaps_legacy_parking_csv` 컬럼으로 겹치는 행을 표시해뒀지만, 이제 어느 한쪽만 검색돼도 불완전하게 보이지는 않습니다.
- **재입장 규정**: 대부분 파일은 `status`/`evidence_type` 필드명을 쓰는데, `docs/KBO_반입물품_재입장규정.md`·`.json`의 재입장 부분만 `reentry_status`/`reentry_evidence_type`으로 필드명이 다릅니다(반입물품 부분과 재입장 부분이 신뢰도가 다르기 때문에 일부러 분리함). 청킹/프롬프트 설계 시 이 필드명 차이를 놓치지 않아야 합니다.
- **포항 특별경기 3건**: `kbo_schedule_full.csv`의 `stadium_code=OTHER` 3행(2026-05-19~21, KT@삼성)은 주변 정보(맛집·편의시설·교통·주차)가 전혀 없습니다. `docs/포항_특별경기_예외처리.md`에 권장 처리 로직이 있는데, **이건 순수 시맨틱 검색만으로는 안전하게 안 걸러질 수 있어서 백엔드/RAG 체인에서 명시적 분기 처리를 권장**합니다 — 검색에만 맡기면 대구 정보를 잘못 붙여줄 위험이 있습니다.

## 5. 이질적인 값 체계를 쓰는 파일 (주의)

- `구장편의시설.csv`의 `evidence_type` 컬럼은 다른 파일과 달리 `OFFICIAL_MAP`/`OFFICIAL_APP_LAYER`/`VISIT_GUIDE`/`RECENT_VISIT`/`MULTI_USER_REPORT` 같은 세분값을 그대로 쓰고 있습니다(다른 파일처럼 `OFFICIAL`/`UNOFFICIAL` 4개로 정규화되어 있지 않음). 이 파일만 놓고 필터링 로직을 짜면 다른 파일과 다르게 동작할 수 있습니다.
- `구장편의시설.csv`·`구장잔여정보_좌석주차버스.csv`·`구장편의시설_보류이력.csv`의 `status` 값도 `CONFIRMED_OFFICIAL`/`OFFICIAL_APPROXIMATE`/`FIELD_VERIFIED`/`HISTORICAL_OFFICIAL`처럼 3번의 공통 6개 값과 다른 값을 씁니다. 이 세 파일은 팀원이 별도로 만든 보완자료라 값 체계를 통일하지 못한 상태입니다 — 오늘 저희가 새로 만들거나 손댄 파일이 아니라 원래부터 이랬던 부분이라, 통일이 필요하면 별도로 논의가 필요합니다.

## 6. PENDING/미결 항목 (청킹 우선순위 판단 필요)

- `3차_신규확보데이터.csv`의 14건 중 6건(`incorporation_status=PENDING_NEW_SCHEMA`)은 수원 입장시간, 창원 시즌권 혜택처럼 아직 전용 스키마가 없는 원문 그대로입니다. 질문-답변 형태로 다듬어진 게 아니라서, 그대로 임베딩하면 검색은 되지만 답변 품질이 다른 정제된 데이터보다 떨어질 수 있습니다 — 청킹하되 검색 우선순위를 낮추거나, 일단 제외했다가 나중에 전용 테이블이 생기면 추가하는 방안을 검토해주시면 좋겠습니다.
- KT 반입물품은 여전히 `OPEN`(공식 예외 미확인, 공통기준 적용 중)입니다 — 데이터 공백은 아니지만 답변 시 "KT 고유 예외는 확인되지 않았다"는 톤 유지가 필요합니다.
- `구장티켓가격.csv`에 NC 50행(특정 경기 동적가격 스냅샷)·무료요금 4행 등 그대로 노출하면 오해 살 수 있는 케이스 4가지가 있습니다. 상세 규칙은 `data/preprocessed/README.md`의 "챗봇 응답 규칙 — 구장티켓가격.csv" 섹션에 있습니다.

## 7. 오늘 밤 저희가 다시 검토하면서 실제로 잡은 문제 1건 (참고)

대전 더본코리아 브랜드 데이터에 새 `source_id`를 붙이면서 이미 다른 출처에 쓰이고 있던 번호(S22)를 실수로 재사용할 뻔했다가, 원본 Sources 시트와 대조하는 과정에서 발견해 고쳤습니다(S29로 정정). **이런 종류의 문제 — 저희가 만든 새 ID/필드가 기존 값과 조용히 충돌하는 것 — 는 저희 쪽 점검만으로는 다 못 잡을 수 있어서, 청킹하면서 이상하게 인용되는 부분이 보이면 꼭 알려주세요.**
